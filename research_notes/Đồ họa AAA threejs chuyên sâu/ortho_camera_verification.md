## Q1. For each node/pass: how is view position/depth reconstructed, does it branch on the camera type, and what breaks when near < 0?

### Takeaway
An orthographic projection with near < 0 is well-defined: the projection divides only by (far − near), so rasterized depth is linear and view-position reconstruction through the inverse projection matrix works. Breakage comes from code that assumes a perspective camera. (1) Perspective depth formulas: near < 0 moves the pole of `perspectiveDepthToViewZ` inside the depth range, to d = f/(f−n) = 2/3 for the lab. (2) Logarithms of `near` or `far/near`, giving NaN. (3) Rays from the camera's centre point (`normalize(-viewPos)`, `cameraPosition` ray origins, distance = −viewZ), which flip sign for geometry between the camera plane and the negative near plane. In r186 the following are ortho-correct: SSR, SSS, TRAA/TAAU (since r184), DenoiseNode/Poisson denoise, the SSAO core, and `depth`/`linearDepth`. GTAO is not ortho-correct (fixed in r187), and neither are SSGI, Godrays, volumetric lighting, the Fog nodes, `PassNode.getViewZNode/getLinearDepthNode`, `depthAwareBlur/Blend` and ClusteredLighting. ClusteredLighting returns NaN with near ≤ 0.

### Cited Findings

#### Shared math and helpers (both versions unless noted)
- The docs say the valid range for `OrthographicCamera.near` is "greater than `0` and less than … far", and that `0` is valid for an orthographic camera (identical text in r180 and r186, OrthographicCamera.js:94–98) (code). — [r186 OrthographicCamera.js#L94](https://unpkg.com/browse/three@0.186.1/src/cameras/OrthographicCamera.js#L94); [r180 OrthographicCamera.js#L94](https://unpkg.com/browse/three@0.180.0/src/cameras/OrthographicCamera.js#L94)
- `Matrix4.makeOrthographic` divides only by `(right-left)`, `(top-bottom)` and `(far-near)`. The z row is linear (`c = -1/(far-near)`, `d = -near/(far-near)` for WebGPU; `-2/(f-n)`, `-(f+n)/(f-n)` for WebGL; a reversed-depth variant also exists), so near < 0 is mathematically fine for rasterization (r186 Matrix4.js:1200–1242) (code). — [r186 Matrix4.js#L1200](https://unpkg.com/browse/three@0.186.1/src/math/Matrix4.js#L1200)
- `getViewPosition(uv, depth, projectionMatrixInverse)` multiplies a clip-space position by the inverse projection and divides by w. It works for any invertible projection, including ortho with near < 0 (r180 PostProcessingUtils.js:17–34; r186 :18–37). `getScreenPosition` and `getScreenPositionFromClip` project with the camera matrix (r186 :49–55, :65–68) (code). — [r180 PostProcessingUtils.js#L17](https://unpkg.com/browse/three@0.180.0/src/nodes/utils/PostProcessingUtils.js#L17); [r186 PostProcessingUtils.js#L18](https://unpkg.com/browse/three@0.186.1/src/nodes/utils/PostProcessingUtils.js#L18)
- The orthographic conversions are linear and never divide by `near`. `viewZToOrthographicDepth = (viewZ + near)/(near − far)` (r180/r186 ViewportDepthNode.js:153); `orthographicDepthToViewZ = depth·(near − far) − near` (r180 :165; r186 :177–189 adds a reversed-depth branch). The GLSL twins are in packing.glsl.js:79–86 (r180) (code). — [r180 ViewportDepthNode.js#L153](https://unpkg.com/browse/three@0.180.0/src/nodes/display/ViewportDepthNode.js#L153); [r186 ViewportDepthNode.js#L177](https://unpkg.com/browse/three@0.186.1/src/nodes/display/ViewportDepthNode.js#L177); [r180 packing.glsl.js#L79](https://unpkg.com/browse/three@0.180.0/src/renderers/shaders/ShaderChunk/packing.glsl.js#L79)
- `perspectiveDepthToViewZ = near·far / ((far − near)·depth − far)` (r180 :191; r186 :227–239; GLSL packing r180 :96–98) has a pole at depth = far/(far − near) (code). With n = −300 and f = 600 the pole is at d = 0.6667, where the true ortho viewZ is −300. At the lab's target depth (viewZ −60 → d = 0.4) the formula returns +750 instead of −60. With near = 0 it returns 0 for every d, and with near = 0.1 / far = 600 the pole sits at d = 1.00017, outside the range (computed, `tools/calc.cjs`). — [r180 ViewportDepthNode.js#L191](https://unpkg.com/browse/three@0.180.0/src/nodes/display/ViewportDepthNode.js#L191); [r186 ViewportDepthNode.js#L227](https://unpkg.com/browse/three@0.186.1/src/nodes/display/ViewportDepthNode.js#L227); [calc output](file:///C:/Users/HLC_2021/AppData/Local/Temp/ortho-verify-20261019/tools/calc.cjs)
- `viewZToLogarithmicDepth` clamps `near` to 1e‑6 and takes `log2(-viewZ/near)` (r180 :203–231; r186 :251–282, clamp at :279), so any fragment with viewZ > 0 (behind the camera plane, which is only possible with near < 0) gives NaN (computed: log2(−10/1e‑6) = NaN). This only applies when `logarithmicDepthBuffer` is on (code). — [r186 ViewportDepthNode.js#L251](https://unpkg.com/browse/three@0.186.1/src/nodes/display/ViewportDepthNode.js#L251)
- `ViewportDepthNode` (`depth`, `linearDepth()`, `viewportLinearDepth`) branches on `camera.isPerspectiveCamera` and uses the orthographic formulas for ortho cameras, both for the DEPTH scope (:95) and the LINEAR_DEPTH scope (:109) in r180 and r186 (code). — [r186 ViewportDepthNode.js#L95](https://unpkg.com/browse/three@0.186.1/src/nodes/display/ViewportDepthNode.js#L95)
- `PassNode.getViewZNode()` uses `perspectiveDepthToViewZ` unconditionally (r180 PassNode.js:595–604; r186 :729–738). `getLinearDepthNode()` is built on it and carries the comment `// TODO: just if ( builder.camera.isPerspectiveCamera )` (r180 :628; r186 :762). The DEPTH-scope PassNode (`depthPass`) returns `getLinearDepthNode()` (r180 :670; r186 :810) (code). — [r180 PassNode.js#L595](https://unpkg.com/browse/three@0.180.0/src/nodes/display/PassNode.js#L595); [r186 PassNode.js#L729](https://unpkg.com/browse/three@0.186.1/src/nodes/display/PassNode.js#L729)

#### GTAO (TSL GTAONode, used by the lab's WebGPU path; GLSL GTAOPass/GTAOShader, used by the lab's WebGL path)

Raw depth is used except in the log-depth branch (:286–292). Near/far appear only as references (:183, :191). #### TRAA (r180 used by the lab) / TAAU (r184+)
- r180 TRAANode jitters with `camera.setViewOffset` (:188–222), which OrthographicCamera supports. It picks the closest-depth neighbour on raw depth (:349–374) and reprojects with the velocity buffer (:382). It never uses near/far, so it is camera-agnostic (code). — [r180 TRAANode.js#L188](https://unpkg.com/browse/three@0.180.0/examples/jsm/tsl/display/TRAANode.js#L188)
- r181–r183 TRAA added a previous-depth disocclusion test that always reprojects with `viewZToPerspectiveDepth` (r183 TRAANode.js:499–505), which is wrong for ortho (code). With n = −300 that function maps viewZ −60 to 4.0 (computed), so `closestDepth − previousDepth > depthThreshold` can never fire and disocclusion rejection is silently disabled (inference from the formula). — [r183 TRAANode.js#L499](https://unpkg.com/browse/three@0.183.0/examples/jsm/tsl/display/TRAANode.js#L499)

#### SSGI (added in r181)

#### SSS: screen-space shadows (added in r181)
- `getViewZ` branches on `isPerspectiveCamera` and uses `orthographicDepthToViewZ` for ortho cameras (:342–358). The ray starts at the inverse-projected position (:383) and runs along the light direction in view space (:384–385). The march interpolates view-space positions linearly in screen space and compares view depths (:433–440). It does not depend on camera position, and near is never a divisor (code). — [r186 SSSNode.js#L342](https://unpkg.com/browse/three@0.186.1/examples/jsm/tsl/display/SSSNode.js#L342)

#### Godrays (added in r183)
- The march starts at the camera world position (:288, :460) and heads toward the reconstructed world position, with direction `worldPosition − cameraPosition` (:471–507), a perspective-style converging ray. The accumulated illumination is proportional to `distance(startPosition, worldPosition)` (:567), so with an ortho camera the result depends on where the camera sits on its axis (code). — [r186 GodraysNode.js#L460](https://unpkg.com/browse/three@0.186.1/examples/jsm/tsl/display/GodraysNode.js#L460)
- For DirectionalLight, whose shadow camera is orthographic, the node applies `perspectiveDepthToViewZ( shadowCoord.z, shadowNear, shadowFar )` (:427). The result feeds the distance attenuation `pow(1 − y/shadowFar, distanceAttenuation)` (:567). This is independent of the main camera (code). — [r186 GodraysNode.js#L427](https://unpkg.com/browse/three@0.186.1/examples/jsm/tsl/display/GodraysNode.js#L427)
- The Godrays docs recommend compositing with `depthAwareBlend()` (:29–37). That helper uses `perspectiveDepthToViewZ` unconditionally (depthAwareBlend.js:30–31, :57–60), and so does `depthAwareBlur` (depthAwareBlur.js:27–38) (code). — [r186 depthAwareBlend.js#L30](https://unpkg.com/browse/three@0.186.1/examples/jsm/tsl/display/depthAwareBlend.js#L30); [r186 depthAwareBlur.js#L27](https://unpkg.com/browse/three@0.186.1/examples/jsm/tsl/display/depthAwareBlur.js#L27)

#### Volumetric lighting (VolumeNodeMaterial + VolumetricLightingModel)
- The march runs between `cameraPosition` and `positionWorld` (r180 :41–49; r186 :43–55), a perspective ray. Occlusion compares `linearDepth( viewZToPerspectiveDepth( rayViewZ, cameraNear, cameraFar ) )` with `linearDepth( material.depthNode )` (r180 :80–82; r186 :84–86; test at r186 :159) (code). For ortho cameras `linearDepth(value)` returns the value unchanged (ViewportDepthNode :109 branch), so a perspective-mapped ray depth is compared with a linear ortho scene depth. #### Clustered lighting (added in r185)
- ClusteredLightsNode computes cluster X/Y bounds with the perspective unprojection `view_x = ndc_x · (−view_z) / P[0][0]` (the comment says so explicitly, :482–485; code :486–519). With near = −300, far/near = −2, and both `Math.pow(−2, 1/24)` and `log(−2)` are NaN; near = 0 divides by zero (computed). — [r186 ClusteredLightsNode.js#L482](https://unpkg.com/browse/three@0.186.1/examples/jsm/tsl/lighting/ClusteredLightsNode.js#L482)

#### Raycasting and upstream stance on negative near
- `Raycaster.setFromCamera` for ortho cameras puts the ray origin "in plane of camera" (view z = 0) and points it down −Z (r180 Raycaster.js:126–129; r186 :127–130) (code). Geometry between the camera plane and a negative near plane is therefore rendered but cannot be picked. Related issues, by title only: #28026 "Position the ray origin at near plane rather than camera origin" (open, 2024), and #14916 "Raycaster.setFromCamera is incorrect for back half of OrthographicCamera frustum" (2018). — [r186 Raycaster.js#L127](https://unpkg.com/browse/three@0.186.1/src/core/Raycaster.js#L127); [issue #28026](https://github.com/mrdoob/three.js/issues/28026); [issue #14916](https://github.com/mrdoob/three.js/issues/14916)
- PR #31912 "Examples: Set OrthographicCamera near plane >= 0" (WestLangley; merged 2025‑09‑18, milestone r181) is justified only by "As per the docs, the valid range is between zero and the current value of the far plane." A contributor later asked "What's wrong with negative orthographic near planes? I use them sometimes…", with no reply on the page. — [PR #31912](https://github.com/mrdoob/three.js/pull/31912)

### Inferences
- Classification for the lab's camera:
  - **(a) Safe with ortho and near < 0:** rasterization and depth, `depth`/`linearDepth`, inverse-projection reconstruction, DenoiseNode, Poisson denoise, SSR (r180+), SSS (r181+), TRAA (r180, and r184+), TAAU.
  - **(b) Ortho-incorrect regardless of near, made worse by near < 0** (sign flip or singularity as viewZ → 0): GTAO up to r186, SSGI, Godrays, volumetric lighting, the Fog nodes, RecurrentDenoise in raylength/specular mode.
  - **(c) Hard failure with near ≤ 0:** ClusteredLighting (NaN slices, and perspective tile bounds even with near > 0), log-depth helpers, and anything built on `perspectiveDepthToViewZ` (PassNode `getViewZNode`/`getLinearDepthNode`/`depthPass`, `depthAwareBlur`/`depthAwareBlend`, TRAA r181–r183). With near > 0 these stay wrong but finite and monotonic; near < 0 puts a pole at d = 2/3 inside the range.
- A useful invariance test: moving an ortho camera along its axis while keeping the near/far planes fixed in world space leaves normalized depth bit-identical and shifts view space by a constant z. A node that is correct for ortho must produce identical images. Nodes that use the absolute view position (`normalize(-viewPos)`, `cameraPosition` rays, −viewZ distances, log(near)) cannot pass, and these are exactly the ones flagged in (b) and (c). The runtime test in Q3 confirms this.
- For `normalize(-viewPos)` nodes (GTAO ≤ r186, SSGI), the angular error is about atan(lateral offset / |viewZ|). At the lab's zoom 1 that is 11.7° at the screen edge and 13.4° at the corner with the camera 60 m out, versus 2.0°/2.3° at 360 m and 0.7°/0.8° at 1000 m (computed). For geometry behind the camera plane the error exceeds 90°, i.e. the hemisphere flips. This matches PR #35073's note that the error grows as the camera moves closer.
- Upgrade note: on r181–r183, TRAA's disocclusion test would be silently disabled for the iso camera, so the lab should go straight to r184 or later. r187 fixes GTAONode and GTAOShader only. SSGI, Godrays, volumetric lighting, ClusteredLighting and PassNode viewZ remain perspective-only in r186, and PR #35073 did not touch them.

## Q2. What does the lab already do about the orthographic camera and the negative near plane?

### Takeaway
The lab's own shaders handle the ortho camera correctly: VFX soft-particle depth uses `orthographicDepthToViewZ`, the surface view direction is (0,0,1), and the cutaway uses view-space xy. Fog reconstruction goes through the inverse projection. But the lab relies on stock three.js GTAOPass (WebGL), and on GTAONode + DenoiseNode + TRAANode (WebGPU, r180), with no ortho patches, and nothing in the source mentions or works around the negative near plane. Its height fog measures distance and direction from the camera's centre point, so under ortho the fog depends on the arbitrary camera distance (60 m) and extends behind the camera plane.

### Inferences
- **GTAO (both backends):** at default iso zoom (1) the stock perspective view vector costs little: mean |Δ| ≈ 0.4/255 against the near ≥ 0 equivalent (Q3). When zoomed out below about 0.2, box faces near the bottom of the frame get strongly over-darkened (Q3: 52/255 mean error in the bottom quarter at zoom 0.15).
  - WebGPU fix: copy PR #35073's one-line `viewDir` change into a local GTAONode, or upgrade to r187. The rebuild-on-camera-change keeps it correct.
  - WebGL fix: the upstream GTAOShader patch keys off `PERSPECTIVE_CAMERA`, which the lab's GTAOPass instance pins to 1. The lab must set `gtao.gtaoMaterial.defines.PERSPECTIVE_CAMERA = camera.isPerspectiveCamera ? 1 : 0` and `needsUpdate = true` whenever the camera type changes, even after upgrading.
- **Height fog:** in iso mode the lab's fog sees about 60 m of distance at the focus, against the 17–20 m the presets were matched at, so iso will look foggier than game mode (not measured in the lab). Geometry behind the camera plane gets fog by distance from the camera point, and the in-scatter direction fans out as if from a perspective eye. Moving the camera back with near ≥ 0 would change the fog further (Q3: height fog changed by 64/255 mean). A camera-placement-independent ortho fog needs an ortho branch, for example distance along the camera forward axis from a fixed reference plane, and `dir = camera forward`.
- **TRAA r180 and the VFX/soft-particle and cutaway code** need no change for ortho or near < 0.
- **Avoid with the iso camera unless patched:** ClusteredLighting (any near), Godrays, SSGI, volumetric lighting, `PassNode.getViewZNode`/`getLinearDepthNode`/`depthPass`, `depthAwareBlur`/`depthAwareBlend`.
- **Placement alternative:** keeping near ≥ 0 by moving the iso camera back, e.g. distance 360 / near 0 / far 900, is equivalent for raster, depth, SSS and TRAA (observed in Q3). It shrinks the GTAO/SSGI view-vector error and makes raycasts reach all visible geometry. It does not fix Godrays, fog or ClusteredLighting, and it changes the fog look.

### Inferences
- The runtime data match the static classification:
  - Invariant (ortho-correct): raster, SSS, TRAA, default lights, GTAO with the r187 patch.
  - Placement-dependent (perspective assumptions): stock GTAO, SSGI, Godrays, height fog.
  - Hard failure: ClusteredLighting.

- A negative near does not change GPU cost; the A vs B differences are within noise.
